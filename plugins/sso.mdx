## Overview

The **SSO Integration** plugin connects Studio to your enterprise identity provider. Support for SAML 2.0, OAuth 2.0/OIDC, and SCIM 2.0 enables single sign-on, just-in-time user provisioning, and automated role mapping.

## Key Features

- **SAML 2.0** — integrate with enterprise IdPs (Okta, Azure AD, OneLogin, etc.)
- **OAuth 2.0 / OIDC** — OpenID Connect for modern SSO providers
- **SCIM 2.0** — automatic user provisioning and deprovisioning from your IdP
- **JIT role mapping** — map IdP groups/attributes to Studio roles automatically
- **Domain enforcement** — require SSO login for specific email domains
- **Login method detection** — check if a user should use SSO or password-based login
- **Certificate lifecycle** — one-URL IdP metadata import, multi-certificate rotation windows, and expiry warnings 30 days ahead
- **Hardened SAML validation** — signature, `InResponseTo`, `Conditions`/`Audience`, assertion-replay and signature-wrapping protection
- **Secrets never leave the server** — the IdP client secret is masked in every configuration response, and the SCIM token is shown exactly once

## For Admins: Configuration

### Migrations

The migrations ship in `plugins/pro-sso/migrations/` and are applied by Studio at startup (see [Installation](/installation#database-migrations)):

| File | Purpose |
|------|---------|
| `001_create_sso_tables.sql` | SSO configuration and role mappings |
| `002_scim_token_hash.sql` | SCIM tokens stored as a hash, never in plaintext |
| `003_certificates.sql` | IdP certificate inventory for rotation and expiry tracking |

Tables created: `pro_sso_configs`, `pro_sso_role_mappings`, `pro_sso_certificates`

### Encryption Key

<Callout kind="alert">
  **Set `PRO_SSO_SECRET_KEY` before you store an OAuth/OIDC client secret.** Without it the plugin still starts and SSO still works, but encryption is a logged no-op: the client secret is written to `pro_sso_configs` **in plaintext**. Use a 64-hex-character key (`openssl rand -hex 32`) or any passphrase, which is SHA-256-derived into a key.
</Callout>

- Secrets stored while the key was unset stay readable after you set it and are encrypted the next time the client secret is saved.
- If the key is removed or changed later, already-encrypted secrets can no longer be decrypted and the OAuth code exchange fails — re-enter the client secret after rotating the key.

### Setting Up SAML 2.0

<Steps>
  <Step title="Get your IdP metadata">
    From your identity provider (Okta, Azure AD, etc.), obtain the SAML metadata URL or XML, entity ID, and SSO URL.
  </Step>
  <Step title="Configure SSO in Studio">
    Open **Settings → SSO**, or use the API:

    ```bash
    POST /api/v1/pro/sso/config
    {
      "provider": "saml",
      "enabled": true,
      "entityId": "https://studio.example.com",
      "ssoUrl": "https://idp.example.com/saml/sso",
      "certificate": "-----BEGIN CERTIFICATE-----\n...",
      "metadataUrl": "https://idp.example.com/metadata.xml",
      "enforceSso": true,
      "verifiedDomains": ["example.com"],
      "bypassEmails": ["break-glass-admin@example.com"]
    }
    ```

    With a `metadataUrl`, the **Import** button next to the field fills entity ID, SSO URL, and certificates for you — see *Certificate Lifecycle & Metadata Import* below. Import reads the **saved** metadata URL, so save the configuration first.
  </Step>
  <Step title="Configure your IdP">
    In your IdP, set the ACS (Assertion Consumer Service) URL to:
    ```
    https://your-studio.com/api/v1/pro/sso/saml/callback
    ```
  </Step>
  <Step title="Set up role mappings">
    Map IdP groups or attributes to Studio roles:

    ```bash
    POST /api/v1/pro/sso/role-mappings
    {
      "idpAttribute": "groups",
      "idpValue": "content-editors",
      "cmsRole": "editor",
      "priority": 10
    }
    ```

    Mappings are evaluated by descending `priority`.
  </Step>
  <Step title="Test the integration">
    Use the SAML initiate endpoint to test: `GET /api/v1/pro/sso/saml/initiate`
  </Step>
</Steps>

<Callout kind="alert">
  **SAML assertions are signature-verified (fail-closed).** Every assertion is
  validated against the **active certificate set** before its identity is trusted —
  an unsigned or forged assertion is rejected. Validation also enforces
  `InResponseTo` (consume-once request binding), `Conditions`/`Audience`/`Destination`,
  an assertion-ID replay cache, and a single-assertion guard against
  signature-wrapping (XSW) attacks.
</Callout>

### Certificate Lifecycle & Metadata Import

Instead of pasting entity ID, SSO URL, and certificate by hand, import everything from your IdP's metadata document — on the SSO page with **Import** next to the metadata URL field, or via the API. The fetch is SSRF-guarded (https only, no private targets, no redirects):

```bash
# One-URL setup / refresh: updates entity id, SSO URL, and the certificate set
POST /api/v1/pro/sso/config/import-metadata

# Certificate inventory with expiry countdown
GET /api/v1/pro/sso/config/certificates
```

- **Rotation windows** — the active set holds *multiple* certificates, so an IdP rollover with old + new certs in metadata causes **zero failed logins**; certificates absent from the metadata are retired, expired ones are never consulted.
- **Expiry warnings** — a daily sweep refreshes metadata-configured IdPs and emits a `sso.certificate.expiring` event up to 30 days before a certificate expires (recorded by the Audit plugin with warning severity). The SSO page lists every stored certificate with a badge — green while valid, amber within 30 days of expiry, grey once retired.

The certificate list carries id, status, expiry date, and days left — never the PEM itself.

### Setting Up OAuth 2.0 / OIDC

```bash
POST /api/v1/pro/sso/config
{
  "provider": "oidc",
  "enabled": true,
  "clientId": "your-client-id",
  "clientSecret": "your-client-secret",
  "authorizationUrl": "https://idp.example.com/oauth2/authorize",
  "tokenUrl": "https://idp.example.com/oauth2/token",
  "userinfoUrl": "https://idp.example.com/oauth2/userinfo",
  "scopes": "openid email profile",
  "enforceSso": false
}
```

`provider` is one of `saml`, `oidc`, `google`, `microsoft`, or `github`. `scopes` is a space-separated string (default `openid email profile`).

<Callout kind="info">
  **The client secret is write-only.** `GET`, `POST`, and `PUT /api/v1/pro/sso/config` all return the stored row with `client_secret` replaced by a fixed mask, so an admin UI or a log can never capture it. `GET` additionally shortens the certificate to its first 50 characters; `POST` and `PUT` return it intact, because the admin form sends the certificate back on save and a shortened value would overwrite the stored PEM. Responses use the snake_case column names (`client_secret`, `enforce_sso`, `verified_domains`, …).
</Callout>

Callback URL for your OAuth provider:
```
https://your-studio.com/api/v1/pro/sso/oauth/callback
```

### SCIM 2.0 Provisioning

SCIM enables automatic user lifecycle management from your IdP:

- **Create** — when a user is assigned to Studio in your IdP, they're automatically created in Studio
- **Update** — name, email, and role changes sync automatically
- **Delete/Deactivate** — when a user is removed from Studio in your IdP, their Studio account is deactivated

SCIM endpoint base URL:
```
https://your-studio.com/api/v1/pro/sso/scim/v2/
```

Generate a SCIM bearer token:
```bash
POST /api/v1/pro/sso/config/regenerate-scim-token
# → { "data": { "scimToken": "<plaintext, shown once>" } }
```

<Callout kind="info">
  **SCIM tokens are hashed at rest and shown once.** A token is returned in
  plaintext exactly once: by the regenerate call, or by the create or update
  (`POST` / `PUT /api/v1/pro/sso/config`) that enables SCIM for a configuration
  without a token yet — as `data.scim_token`, 64 hex characters. On the SSO page
  the bearer-token field shows it after **Create**, **Save** or **Regenerate**,
  with **Copy** and **Regenerate** buttons and a notice to copy it now. Every
  later response only shows its first characters followed by a mask; re-enabling
  SCIM keeps an existing token valid. Regenerating invalidates the previous token
  immediately.
</Callout>

**Standards-conformant responses.** All nine `scim/v2/*` routes return the bare RFC 7644 documents your IdP expects — no Studio `{ "data": … }` wrapper — and `meta.created` / `meta.lastModified` carry real ISO 8601 timestamps. The surface implements the interop details large IdPs check during setup: `userName eq "…"` / `externalId eq "…"` filtering for the duplicate check, PATCH operations (including Microsoft Entra's path-less value-object form), the error statuses RFC 7644 prescribes, and the discovery endpoints (`ServiceProviderConfig`, `ResourceTypes`, `Schemas`).

**SCIM errors** are RFC 7644 error documents too, sent as `application/scim+json` — never Studio's `{ code, message }` error body:

```json
{
  "schemas": ["urn:ietf:params:scim:api:messages:2.0:Error"],
  "status": "409",
  "scimType": "uniqueness",
  "detail": "User with userName jane@example.com already exists"
}
```

| Case | Status | `scimType` | `detail` |
|------|--------|------------|----------|
| Unsupported filter | `400` | `invalidFilter` | `Unsupported filter: only userName/externalId eq "value" are supported` |
| Other invalid input | `400` | `invalidValue` | The validation messages |
| `userName` already exists | `409` | `uniqueness` | `User with userName … already exists` |
| Unknown user id | `404` | — | `User … not found` |
| Missing or unknown token | `401` | — | `Missing SCIM bearer token` / `Invalid SCIM token`, plus `WWW-Authenticate: Bearer realm="SCIM"` |
| Server error | `5xx` | — | The status text only; details go to the server log |

| Endpoint | Purpose |
|----------|---------|
| `GET /scim/v2/Users` | List users, with `userName` / `externalId` filters |
| `POST /scim/v2/Users` | Provision a user |
| `GET /scim/v2/Users/:id` | Get one user |
| `PUT` / `PATCH /scim/v2/Users/:id` | Replace or patch a user (activate/deactivate, name, email) |
| `DELETE /scim/v2/Users/:id` | Deactivate the user (`204`) |

Paths are relative to the SCIM base URL above; every call needs `Authorization: Bearer <SCIM token>`. Request bodies may be sent as `application/scim+json` — what Entra ID and Okta send — or as `application/json`, on any Studio host. Bodies are limited like other API requests:

| Request | Status | `scimType` | `detail` |
|---------|--------|------------|----------|
| Body larger than 100 KB | `413` | — | `The request body exceeds 100 KB` |
| Invalid JSON, or neither an object nor an array | `400` | `invalidSyntax` | `The request body is not valid JSON` |
| A charset other than UTF-8, or a `Content-Encoding` other than identity | `415` | — | — |

### Domain Enforcement

When SSO is enforced (`enforceSso`) for the organization's `verifiedDomains`, users with a matching email address are sent to SSO login instead of the password form. Addresses on `bypassEmails` keep password login — use this for a break-glass admin account.

```bash
# Login screen, before authentication (30 requests/minute per client address)
POST /api/v1/pro/sso/login-method
{ "organizationSlug": "acme", "email": "user@example.com" }
# → { "data": { "method": "sso" } }   or   { "data": { "method": "password" } }

# Same check for the caller's own organization (authenticated)
POST /api/v1/pro/sso/check-login-method
{ "email": "user@example.com" }
```

The public probe answers `password` for unknown organization slugs, so it reveals nothing about which organizations or accounts exist. The 31st request within a minute from one client address answers `429` with code `RATE_LIMITED` and a `Retry-After` header. Behind Studio's reverse proxy, the client address is the one the proxy appends to `X-Forwarded-For` (or sets as `X-Real-IP`); on a direct connection it is the socket address. Forwarding headers a client sends itself do not change its bucket.

<Callout kind="info">
  This assumes **one** reverse proxy in front of the API (for example Caddy), as in the standard deployment. With a second internal hop — a load balancer in front of the proxy — the rightmost forwarded address is the load balancer's, and all clients share one bucket.
</Callout>

## For Editors: Logging In

When SSO is configured, the login page shows a **Sign in with SSO** button (or redirects automatically if domain enforcement is enabled). Click it, authenticate with your organization's identity provider, and you'll be logged into Studio with your assigned role.

<Callout kind="info">
  If your admin has configured role mappings, your Studio role is determined by your IdP groups — you don't need to ask an admin to set your role manually.
</Callout>
