## Overview

The **Content Import** plugin lets you bulk-import content from external sources. Map source fields to content type fields, validate every record against the content type's schema, preview the import before committing, detect duplicates, and roll back if something goes wrong.

## Key Features

- **Five source formats** — JSON, CSV, XML, WordPress (WXR), and Markdown with frontmatter
- **Schema validation** — every record is validated against the target content type before insert
- **Field mapping** — map source columns/keys to content type fields with transforms; target suggestions come from the content type's form, and dot paths fill nested fields
- **Asset and relation transforms** — turn an image URL into a Studio asset, or a foreign value into a content relation
- **Duplicate detection** — detect by slug or any field value, including nested paths
- **Preview mode** — dry-run on the first N records before committing
- **Background processing** — large files run as jobs with progress, cancellation, and size limits
- **Retry** — re-run only the failed rows
- **Rollback** — delete all content (and assets) created by a specific import job

## For Admins: Setup

### Migrations

The Studio API applies and tracks plugin migrations itself at startup, so these run automatically — a new one takes effect on the next API start. Run them by hand only if you set `PLUGIN_MIGRATIONS=off` because a deploy step applies them; see [Installation](/installation) for details.

```bash
psql -U postgres -d roadbeat_studio -f plugins/pro-import/migrations/001_create_import_tables.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-import/migrations/002_add_organization_id_to_imported_content.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-import/migrations/003_extend_job_statuses.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-import/migrations/004_extend_import_sources.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-import/migrations/005_track_imported_assets.sql
```

Tables created: `pro_import_jobs`, `pro_imported_content`, `pro_imported_assets`

### Limits and configuration

| Variable | Default | Purpose |
|----------|---------|---------|
| `IMPORT_STALE_HOURS` | `2` | A job stuck in `processing` for longer is swept and marked failed, so a dead worker cannot wedge it forever |
| `IMPORT_ASSET_MAX_BYTES` | `26214400` (25 MB) | Largest asset the `asset` transform will download |
| `IMPORT_ASSET_TIMEOUT_MS` | `20000` | Per-asset download timeout |

Inline uploads (`fileContent`) are capped at 5 MB by the API. For larger files, upload to storage first and pass a `fileKey`.

## For Editors: Importing Content

### Import Workflow

<Steps>
  <Step title="Navigate to Content Import">
    Go to **Content Import** in the sidebar.
  </Step>
  <Step title="Choose the source format">
    Pick JSON, CSV, XML, WordPress, or Markdown. Each format shows its own options — a record selector for XML, a post-type picker for WordPress, a ZIP-bundle switch for Markdown.
  </Step>
  <Step title="Pick the target content type">
    Choose the content type from the list of your organization's content types — there is no id to type in.
  </Step>
  <Step title="Upload your file and map fields">
    Each mapping target field suggests the content type's form fields as you type (see [Field Mapping](#field-mapping)). WordPress and Markdown offer a preset that fills the mapping table with the field names their parser produces, so a migration usually needs no hand-mapping.
  </Step>
  <Step title="Preview (recommended)">
    Run a preview to see how the first records would be imported, including schema-validation errors and duplicate conflicts.
  </Step>
  <Step title="Process the import">
    Execute the import. Progress is tracked per row, and a long-running job can be cancelled.
  </Step>
  <Step title="Review results">
    Check the job status for errors. Failed rows can be retried on their own.
  </Step>
</Steps>

### Source Formats

<Tabs>
  <Tab title="JSON" icon="braces">
    An array of objects, or a single object. Nested values are addressed with dot paths.
  </Tab>
  <Tab title="CSV" icon="table">
    Delimiter and UTF-8 byte-order mark are detected automatically; you can still override the delimiter.
  </Tab>
  <Tab title="XML" icon="code">
    Set a **record selector** — a dot path to the repeated node, e.g. `catalog.product`. Leave it blank to auto-detect the repeated element.
  </Tab>
  <Tab title="WordPress" icon="globe">
    Upload the XML from **Tools → Export** in WordPress. Choose which post types to import and whether to include drafts.
  </Tab>
  <Tab title="Markdown" icon="file-text">
    A single `.md` file or a `.zip` of them. Frontmatter keys become fields, the body becomes `content`, and `_slug` is derived from the filename.
  </Tab>
</Tabs>

### Migrating from WordPress

<Steps>
  <Step title="Export from WordPress">
    In WordPress, go to **Tools → Export** and choose **All content**. You get a `.xml` file — a WXR export.
  </Step>
  <Step title="Select the WordPress format">
    Upload the file and pick **WordPress (WXR export)** as the format.
  </Step>
  <Step title="Pick post types">
    Run a preview once — the picker then lists the post types your export actually contains, rather than the usual defaults. Select what you want and decide whether drafts come along.
  </Step>
  <Step title="Apply the preset mapping">
    Click **Apply preset mapping**. It fills in `title`, `slug`, `content`, `excerpt`, `publishedAt`, `author`, `tags`, and `categories`. Rows you already edited are left untouched.
  </Step>
  <Step title="Preview, then import">
    Preview to catch schema mismatches, then run the import.
  </Step>
</Steps>

### Field Mapping

Map each target field of the content type to a source field. The **key** of a mapping is the target path *inside the content item's data*; the **value** is the source column, key or dot path in your file:

```json
{
  "contentTypeId": "news",
  "source": "csv",
  "config": {
    "fieldMappings": {
      "headline.en": "Title",
      "article_body.en": "Body",
      "seo.meta_title": "SEO Title",
      "dates.date_published": { "source": "Date", "transform": "date" }
    },
    "slugField": "Slug",
    "skipDuplicates": true,
    "duplicateKey": "headline.en"
  }
}
```

#### What to enter as a target

- **Use the field ids the mapping table suggests.** They come from the content type's editor form and are the exact paths the content editor reads and writes — for example `headline`, `seo.meta_title` or `dates.date_published`. Platform-managed blocks (`identifier`, `ai_metadata`, `moderation`, …) are not offered because Studio fills them itself.
- **Dots create nested values.** `seo.meta_title` is written as `{ "seo": { "meta_title": … } }`, creating the intermediate objects as needed. A target without dots writes a top-level field, exactly as before.
- **Translatable fields take a language suffix.** Text the editor stores per language (such as `headline`) is addressed as `headline.en`, `headline.de`, …
- **Registry form ids are translated for you.** Some content types use a different id in their Schema Registry form than in storage — the quote type's `quote_text` is stored at `content.text`, its `author` at `attribution.author`. A mapping (or `duplicateKey` / `slugField`) that names the registry id is rewritten to the storage path when the job is created, previewed and processed, so the imported text shows up in the editor.
- **Do not prefix targets with `data.`** — the target is already relative to the content data.

<Callout kind="info">
  `duplicateKey` is a target path as well (or `slug`). It must be produced by one of your mappings — a key whose first segment matches no mapping target is rejected with `400` (`IMPORT_DUPLICATE_KEY_UNMAPPED`) when the job is created, because it could never match anything. Nested keys such as `headline.en` are compared at their full path.
</Callout>

#### Generated slugs

`slugField` names a **source** column to take the slug from. Without it, Studio derives the slug from the record's `headline`, `title` or `name`. Content types that have none of these (quotes, jokes, check-ins, …) get a slug from the first meaningful text instead — fields with text-like names (`text`, `quote`, `summary`, `caption`, `label`, …) are tried before others such as `author`, and URLs, `identifier` and `seo` blocks are skipped. Only when no usable text exists does the slug fall back to `import-<timestamp>-<random>`. Slugs are made unique per content type and locale.

### Available Transforms

| Transform | Description |
|-----------|-------------|
| `lowercase` | Convert to lowercase |
| `uppercase` | Convert to uppercase |
| `trim` | Remove leading/trailing whitespace |
| `number` | Parse as number |
| `boolean` | Parse as boolean |
| `date` | Parse as ISO date |
| `json` | JSON stringify |
| `asset` | Download the value (a URL) and store it as an organization asset |
| `relation` | Resolve the value to an existing content item and store the relation |

### Importing Assets and Relations

The `asset` transform turns an image-URL column into a real Studio asset:

```json
{
  "image": {
    "source": "ImageUrl",
    "transform": "asset",
    "assetConfig": { "onError": "null" }
  }
}
```

Downloads are checked against the file's actual magic bytes — not the URL extension or the server's declared content type — and URLs resolving to private or internal addresses are rejected.

The `relation` transform resolves a foreign value into a content id:

Both transforms write to nested targets like any other mapping.

```json
{
  "author": {
    "source": "AuthorSlug",
    "transform": "relation",
    "relationConfig": { "contentType": "person", "matchField": "slug", "onMiss": "null" }
  }
}
```

`onMiss` decides what happens when nothing matches: `null` (default), `skip` the row, or `fail` the row.

### Validation

Every record is validated against the target content type's JSON Schema before it is written.

<Callout kind="tip">
  `validationMode` controls what happens to an invalid record: `strict` (the default) counts it as failed and reports the field-level errors; `skipInvalid` skips it quietly.
</Callout>

### Rollback

If an import produces bad data, roll back everything that job created:

```bash
POST /api/v1/pro/import/jobs/:id/rollback
```

This deletes the content items **and** any assets the import downloaded, so a rolled-back import leaves nothing behind in object storage.

<Callout kind="alert">
  If deleting a content item fails, its tracking row is kept so the rollback can be retried. A rollback that reports errors has not finished — re-run it.
</Callout>

## API Reference

All import endpoints are in the [Studio API Reference](https://docs.studio.roadbeat.dev/api-reference/overview) under the `pro-import` tag.

| Endpoint | Description |
|----------|-------------|
| `GET /api/v1/pro/import/jobs` | List import jobs |
| `POST /api/v1/pro/import/jobs` | Create an import job |
| `POST /api/v1/pro/import/jobs/:id/process` | Execute the import |
| `POST /api/v1/pro/import/jobs/:id/cancel` | Cancel a running import |
| `POST /api/v1/pro/import/jobs/:id/retry` | Retry failed rows |
| `POST /api/v1/pro/import/jobs/:id/rollback` | Roll back imported content and assets |
| `POST /api/v1/pro/import/preview` | Preview import (dry-run) |
