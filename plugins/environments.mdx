## Overview

The **Environments** plugin lets you manage multiple content environments — development, staging, and production. Promote content between environments, compare differences, clone environments for testing, and use aliases for zero-downtime environment switching.

## Key Features

- **Environment CRUD** — create named environments with slug, color, and sort order
- **Production flag** — exactly one environment is marked as production (atomic switch)
- **Content promotion** — promote individual content items between environments, optionally **with their reference closure** (referenced entries come along, ids remapped)
- **Conflict-safe** — promoting over target-side edits made after the last promotion fails with 409 unless you pass `force`
- **Bulk sync** — sync all content between two environments with content type and status filters
- **Environment comparison** — diff content between two environments (only_a, only_b, same_version, different_version) including **broken-reference flags** per side
- **Cloning** — clone an environment with optional content copy
- **Aliases** — named pointers to environments for zero-downtime switching (e.g., "master" → production)
- **Sync logs** — track all promote/sync/clone operations

## For Admins: Setting Up Environments

### Migration

```bash
psql -U postgres -d roadbeat_studio -f plugins/pro-environments/migrations/001_create_environment_tables.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-environments/migrations/002_org_match_trigger.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-environments/migrations/003_lifecycle_hardening.sql
```

Tables created: `pro_environments`, `pro_environment_aliases`, `pro_environment_content`, `pro_sync_logs`

### Seeding Default Environments

Create the standard production/staging/development environments:

```bash
POST /api/v1/pro/environments/seed
```

This creates three environments with appropriate colors and sort orders, plus a "master" alias pointing to production.

### Promoting Content

Move content from one environment to another:

```bash
POST /api/v1/pro/environments/promote
{
  "contentId": "uuid",
  "fromEnvironmentId": "staging-id",
  "toEnvironmentId": "production-id",
  "includeReferences": true,
  "maxReferenceDepth": 3
}
```

With `includeReferences`, promotion copies the entry's **reference closure**: entries it references (per the content type's schema-declared reference fields) are promoted first, and reference ids in the copied data are **remapped to the target-environment copies** — a promoted article arrives with a resolvable author instead of a dangling source-environment id. Cycles are handled; `maxReferenceDepth` caps the walk (default 3).

The response reports `cascaded` (referenced entries promoted alongside), `remappedReferences`, and `skippedReferences` (referenced entries left untouched because the target copy has newer edits — only the *root* entry enforces the 409/`force` conflict rule, so one stale author never aborts a whole article promotion).

<Callout kind="alert">
  **Newer target edits are never silently overwritten.** If the target copy was
  modified after the last promotion, the promote fails with **409**; re-run with
  `"force": true` to overwrite deliberately. Forced overwrites are recorded in the
  sync log.
</Callout>

<Callout kind="info">
  New copies in the target environment get a `--<environment-slug>` suffix on their
  slug (content slugs are unique per organization, not per environment), and sync
  logs report **real** `items_total` / `items_synced` / `items_failed` counts.
</Callout>

### Bulk Sync

Sync all content between environments:

```bash
POST /api/v1/pro/environments/sync
{
  "fromEnvironmentId": "staging-id",
  "toEnvironmentId": "production-id",
  "contentTypeFilter": "news",
  "statusFilter": "published"
}
```

### Comparing Environments

See what differs between two environments:

```bash
POST /api/v1/pro/environments/compare
{
  "environmentAId": "staging-id",
  "environmentBId": "production-id"
}
```

Returns categorized content: items only in A, only in B, same version in both, or different versions. Each row also carries `brokenRefsA` / `brokenRefsB` — the number of referenced entries **not mapped into the same environment** — so content promoted without its closure is flagged instead of silently mis-rendering in delivery.

### Cloning

Create a sandbox by cloning an existing environment:

```bash
POST /api/v1/pro/environments/:id/clone
{
  "name": "Feature Branch Test",
  "slug": "feature-test",
  "includeContent": true,
  "contentTypeFilter": "news"
}
```

Cloning with `includeContent` runs as **one transactional, set-based copy** — an aborted clone leaves zero orphaned content rows, only the empty environment (which is then removed).

### Aliases

Aliases are named pointers that can be atomically switched between environments:

```bash
# Create alias
POST /api/v1/pro/environments/aliases
{ "alias": "live", "environmentId": "production-id", "description": "Live content" }

# Switch alias to a different environment (zero-downtime)
PUT /api/v1/pro/environments/aliases/:id
{ "environmentId": "new-production-id" }

# Resolve an alias to its environment ID
POST /api/v1/pro/environments/aliases/resolve
{ "identifier": "live" }
```

<Callout kind="alert">
  **Deleting an environment that aliases point at fails with 409**, listing the
  affected aliases. Re-point them first — an alias like `master` is a stable
  contract consumers depend on, and it must never vanish as a side effect.
</Callout>

## For Editors: Working with Environments

When environments are configured, editors may see an environment selector in the admin UI. Content created in one environment is isolated from other environments until explicitly promoted.

Typical workflow:

1. Create and edit content in the **Development** environment
2. When ready, promote to **Staging** for review
3. After approval, promote to **Production** to go live

<Callout kind="info">
  Only admins can promote, sync, and manage environments. Editors work within their assigned environment.
</Callout>
