## Overview

The **Content Locking** plugin prevents concurrent editing conflicts by allowing users to acquire locks on content items. As soon as a user makes their first change in the editor, an **exclusive lock** is acquired automatically — other users are blocked from saving changes until the lock is released.

## Key Features

- **Lock on first edit** — the editor panel acquires the lock with your first keystroke or field change; just opening an item does not lock it
- **Exclusive locks** — blocks other users from saving, deleting, or publishing (default)
- **Advisory locks** — warns other users but doesn't block (for soft collaboration)
- **Auto-expiring** — locks expire after a configurable TTL (default 5 minutes) without a heartbeat
- **Instant release on tab close** — a `sendBeacon` release frees the lock within seconds instead of waiting out the TTL
- **Heartbeat extension** — the editor sidebar automatically extends the lock every 2 minutes
- **Polite takeover** — blocked editors can *request access*; the holder gets a notification
- **Force-unlock** — same-organization admins can break any lock; the action is audited and the displaced editor is notified
- **Lock management** — view all active locks and the audit trail across the organization
- **Localized messages** — lock banners use structured codes translated into all 24 EU locales

## For Admins: Configuration

### Migrations

The Studio API applies the plugin's migrations **automatically on its next start** — see [Installation](/installation). If your deployment applies them in a separate step (`PLUGIN_MIGRATIONS=off`), run them in order:

```bash
psql -U postgres -d roadbeat_studio -f plugins/pro-locking/migrations/001_create_content_locks_table.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-locking/migrations/002_add_organization_id.sql
psql -U postgres -d roadbeat_studio -f plugins/pro-locking/migrations/003_takeover_and_beacon.sql
```

Tables created: `pro_content_locks`, `pro_lock_audit`

### Configuration

| Environment variable | Default | Description |
|----------------------|---------|-------------|
| `LOCK_TTL_SECONDS` | `300` | Lock lifetime without a heartbeat; surfaced via the API so UI expiry hints stay accurate |

### Managing Locks

Navigate to **Content Locks** in the sidebar to view all active locks. From here you can:

- See who holds each lock and when it was acquired
- **Force-unlock** any content item if a lock is stuck or a user is unavailable (admins only)
- Review the **audit trail** (`GET /api/v1/pro/locking/audit`) — every force-unlock and takeover request is recorded with actor and previous holder

<Callout kind="alert">
  Force-unlocking may cause the locked user to lose unsaved changes. The displaced editor is notified immediately that saving may now conflict — but coordinate with the lock holder when possible.
</Callout>

## For Editors: Working with Locks

### Automatic Locking

When you open a content item in the editor, the **Lock Status** sidebar panel shows whether anyone holds a lock. Opening an item only to read it does not lock it. Then the panel:

1. Acquires an exclusive lock on your **first edit** — the first input or change anywhere in the editor area (or immediately, if you click **Lock for Editing**)
2. Shows the lock status (locked by you) and when it expires
3. Sends heartbeat pings every 2 minutes to keep the lock alive, and re-acquires the lock if it expired in the meantime
4. Releases the lock when you navigate away — **including on tab or browser close**, via a `sendBeacon` call, so teammates are unblocked within seconds instead of after the TTL

### If Content Is Locked by Someone Else

If another user holds the lock, you'll see:

- **Who** holds the lock
- That **saving is blocked** until the lock is released — save, delete and publish requests are rejected with `403`; your edits do not acquire a lock

You can click **Request access** to send the current holder a polite takeover notification, wait for them to finish, or ask an admin to force-unlock.

### Lock Types

| Type | Behavior |
|------|----------|
| **Exclusive** (default) | Other users cannot save — their update requests are blocked with a `403 Forbidden` |
| **Advisory** | Other users see a warning but can still save — useful for soft collaboration |

## Event Integration

The plugin guards `content.beforeUpdate`, `content.beforeDelete`, and `content.beforePublish`. When another user tries to save, delete, or publish content that has an exclusive lock held by someone else, the event is **prevented** and CE throws a `ForbiddenException` — a lock that didn't survive a delete or publish would be a false safety promise. Advisory locks stay warn-only.

It also emits two events, which the [Notifications](/plugins/notifications) plugin turns into in-app notifications:

| Event | Recipient |
|-------|-----------|
| `lock.force_unlocked` | The editor whose lock an admin broke |
| `lock.takeover.requested` | The current lock holder, when someone clicks **Request access** |

<Callout kind="info">
  Before the November 2026 update these two events never left the plugin, so neither notification was delivered, and the editor panel only showed the lock status — a lock existed only if someone clicked the lock button. Both now work as described on this page.
</Callout>

## API Reference

All locking endpoints are in the [Studio API Reference](https://docs.studio.roadbeat.dev/api-reference/overview) under the `pro-locking` tag.

| Endpoint | Description |
|----------|-------------|
| `POST /api/v1/pro/locking/content/:id/lock` | Acquire a lock |
| `DELETE /api/v1/pro/locking/content/:id/lock` | Release a lock (owner only) |
| `POST /api/v1/pro/locking/content/:id/lock/extend` | Heartbeat extend |
| `GET /api/v1/pro/locking/content/:id/lock` | Check lock status |
| `POST /api/v1/pro/locking/content/:id/lock/force` | Force-unlock (same-org admin only; audited) |
| `POST /api/v1/pro/locking/content/:id/lock/request` | Request the lock from its holder (polite takeover) |
| `POST /api/v1/pro/locking/content/:id/lock/release-beacon` | Beacon release on tab close (release-token credential) |
| `GET /api/v1/pro/locking/locks` | List all active locks (+ configured TTL) |
| `GET /api/v1/pro/locking/audit` | Lock audit trail (admin only) |
