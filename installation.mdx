## Overview

Studio Pro is delivered as either a **pre-built Docker image** (recommended) or as **npm packages** you install into an existing Studio CE instance. Both methods result in the same outcome — Pro plugins loaded at runtime by CE's plugin system.

## Option A: Docker Image (Recommended)

The simplest deployment method. The Pro Docker image is the CE base image with all Pro plugins pre-installed.

<Steps>
  <Step title="Get registry credentials">
    Your Pro license includes access to the private Docker registry at `registry.roadbeat.dev`. You'll receive credentials when your license is activated.
  </Step>
  <Step title="Log in to the registry">
    ```bash
    docker login registry.roadbeat.dev
    ```
  </Step>
  <Step title="Update your docker-compose.yml">
    Replace the CE image with the Pro image:

    ```yaml
    services:
      api:
        image: registry.roadbeat.dev/studio-pro:latest
        environment:
          ROADBEAT_LICENSE_KEY: ${ROADBEAT_LICENSE_KEY}
          PLUGINS_DIR: /app/plugins
          # ... same env vars as CE
    ```
  </Step>
  <Step title="Set the license key and plugin secrets">
    Add your license key to `.env`, together with the [plugin secrets](#plugin-secrets) for the plugins you run:

    ```bash
    ROADBEAT_LICENSE_KEY=eyJhbGciOiJFZDI1NTE5...
    INTEGRATIONS_KEK=<openssl rand -base64 32>
    PRO_AI_VAULT_KEK=<openssl rand -base64 32>
    PRO_SSO_SECRET_KEY=<openssl rand -hex 32>
    AUDIT_PSEUDONYM_SECRET=<openssl rand -base64 32>
    ```
  </Step>
  <Step title="Start the stack">
    ```bash
    docker compose up -d
    ```

    On startup the API applies the plugins' database migrations (see [Database Migrations](#database-migrations)), then loads the Pro plugins. Check the logs to confirm:

    ```bash
    docker compose logs api | grep -i "plugin"
    ```
  </Step>
</Steps>

## Option B: Manual Plugin Installation

Install Pro plugins into an existing CE instance via the private npm registry.

<Steps>
  <Step title="Configure npm registry access">
    ```bash
    npm config set @roadbeat-pro:registry https://npm.roadbeat.dev
    npm login --scope=@roadbeat-pro
    ```
  </Step>
  <Step title="Install plugins">
    ```bash
    cd /path/to/studio
    mkdir -p plugins

    # Install individual plugins
    npm install @roadbeat-pro/workflows --prefix plugins/pro-workflows
    npm install @roadbeat-pro/scheduling --prefix plugins/pro-scheduling
    # ... repeat for each licensed plugin
    ```
  </Step>
  <Step title="Set environment variables">
    ```bash
    ROADBEAT_LICENSE_KEY=eyJhbGciOiJFZDI1NTE5...
    PLUGINS_DIR=./plugins
    ```

    Add the [plugin secrets](#plugin-secrets) for the plugins you installed.
  </Step>
  <Step title="Restart Studio">
    ```bash
    pnpm --filter api dev
    ```

    The API applies the plugins' SQL migrations on startup, before the plugins initialize — no separate migration step. See [Database Migrations](#database-migrations).
  </Step>
</Steps>

## Verifying Installation

After startup, verify Pro plugins are loaded:

```bash
# Check the plugin manifest endpoint
curl http://localhost:3000/api/v1/plugins/manifest
```

The response should list your licensed plugins:

```json
{
  "edition": "pro",
  "tier": "team",
  "activePluginIds": ["pro-workflows", "pro-scheduling", "pro-audit", ...],
  "plugins": [...]
}
```

<Callout kind="tip">
  In the Admin UI, Pro plugins appear as new menu items in the sidebar. You should see sections like "Workflows & Publishing", "Content Tools", etc.
</Callout>

## Plugin Secrets

Several plugins encrypt credentials or key pseudonyms with a secret you provide through the environment. Set them **before** the plugins store their first secret — some only take effect for values written afterwards.

<Callout kind="alert">
  Most of these degrade **silently** when unset: the plugin starts and works, only without the protection. The vault keys (`INTEGRATIONS_KEK`, `PRO_AI_VAULT_KEK`, `LAYOUTS_KEK`) are the exception — with `NODE_ENV=production` (or `REQUIRE_VAULT_KEK=true`) the plugin refuses to start without one. A vault key (any `*_KEK`) that is set but is not base64-encoded 32 bytes always stops the plugin.
</Callout>

| Variable | Plugin | Consequence if unset |
|----------|--------|----------------------|
| `PRO_SSO_SECRET_KEY` | pro-sso | IdP client secrets are stored **unencrypted** — encryption becomes a logged no-op. A 64-hex-character key (`openssl rand -hex 32`) or any passphrase (SHA-256 derived). |
| `AUDIT_PSEUDONYM_SECRET` | pro-audit | GDPR erasure pseudonyms are keyed by a value published in the plugin source, so `erased-user-<hex>` is re-identifiable by anyone who can guess a user ID. Logged as a warning at startup. Setting it later changes the pseudonym for subsequent erasures — see [Audit Logging](/plugins/audit#pseudonym-secret). |
| `PRO_AI_VAULT_KEK` | pro-ai | Outside production, AI provider credentials are encrypted with an insecure built-in development key and `GET /api/v1/pro/ai/status` reports `vaultKeyMode: "insecure-dev"`. In production the plugin does not start. Base64-encoded 32 bytes. |
| `INTEGRATIONS_KEK` | pro-integrations | Same behaviour as `PRO_AI_VAULT_KEK` for connection credentials. Also the fallback key for the three variables below. Base64-encoded 32 bytes. |
| `LAYOUTS_KEK` | pro-layouts | Falls back to `INTEGRATIONS_KEK`; without either, the Git sync access token uses an insecure development key — and in production the plugin does not start. |
| `API_EXPLORER_KEK` | pro-api-explorer | Falls back to `INTEGRATIONS_KEK`; without either, saving secrets in an API Explorer environment is refused (`400 VAULT_KEY_MISSING`). |
| `EXPORT_DELIVERY_KEK` | pro-export | Falls back to `INTEGRATIONS_KEK`; without either, scheduled exports that need delivery credentials are refused (`400 VAULT_KEY_MISSING`); schedules without credentials still work. |
| `INTEGRATIONS_METRICS_TOKEN` | pro-integrations | The Prometheus endpoint `GET /api/v1/pro/integrations/metrics` is served **without authentication** — your network is then the only boundary. When set, scrapers must send `Authorization: Bearer <token>`. |

Generate the base64 keys with `openssl rand -base64 32`. Keep every key in your secret store: losing a vault key makes the credentials it encrypted unreadable, and changing `PRO_SSO_SECRET_KEY` means re-entering the IdP client secret.

<Callout kind="info">
  The [Studio CE configuration reference](https://studio-docs.roadbeat.net/deployment/configuration) documents `PRO_SSO_SECRET_KEY`, `PRO_AI_VAULT_KEK`, and `AUDIT_PSEUDONYM_SECRET` alongside the CE variables.
</Callout>

## Database Migrations

Each plugin ships its tables as plain SQL files in its `migrations/` directory, and the shared plugin base ships its own in `packages/plugin-base/migrations/`. **The Studio API applies them itself** — there is no separate migration command:

1. On startup, after plugin discovery and **before** any plugin initializes, the API applies the plugin-base migrations first, then each discovered plugin's files in file-name order.
2. Every applied file is recorded in the `plugin_migrations` table (plugin, file name, checksum, time) and never run again.
3. Each file runs in one transaction. Statements whose objects already exist are skipped, so installations whose tables were created by hand are baselined automatically on the first start.
4. Any other error rolls the whole file back, records nothing, and skips that plugin's later migrations. The API still starts and logs the failure — check the log for `Plugin migration … failed` after an upgrade.
5. A file that changed after it was applied is reported (`changed after it was applied — not re-run`), not re-executed.

New migrations that ship with a plugin update are applied on the next API restart.

<Callout kind="tip">
  To apply migrations in a deploy step instead (for example with a database role the API does not have), set `PLUGIN_MIGRATIONS=off` and run the files yourself, plugin base first, each plugin in file-name order:

  ```bash
  psql -U postgres -d roadbeat_studio -f packages/plugin-base/migrations/001_create_retention_settings.sql
  psql -U postgres -d roadbeat_studio -f plugins/pro-workflows/migrations/001_create_workflow_tables.sql
  # … every file of every installed plugin, in order
  ```

  `PLUGIN_BASE_MIGRATIONS_DIR` overrides where the API looks for the plugin-base files (default `<PLUGINS_DIR>/../packages/plugin-base/migrations`).
</Callout>

See [Plugin database migrations](https://studio-docs.roadbeat.net/plugins/overview#plugin-database-migrations) in the Studio CE documentation for the runner's details.

## Updating

<Tabs>
  <Tab title="Docker" icon="server">
    ```bash
    docker compose pull
    docker compose up -d
    ```

    The new image's plugin migrations are applied when the API starts.
  </Tab>
  <Tab title="Manual" icon="terminal">
    ```bash
    # Update each plugin package
    npm update @roadbeat-pro/workflows --prefix plugins/pro-workflows

    # Restart — new migrations are applied on startup
    pnpm --filter api dev
    ```

    With `PLUGIN_MIGRATIONS=off`, apply the plugin's new migration files yourself before restarting.
  </Tab>
</Tabs>

<Callout kind="info">
  **Upgrading from releases before November 2026:** three migrations are new — `pro-workflows/006_drop_workflow_is_default.sql` (removes the unused "default workflow" flag), `pro-workflows/007_manual_tasks.sql` (manual tasks and the task board), and `pro-export/006_job_error_message.sql` (failed export jobs keep their reason). Your existing, hand-created tables are detected and recorded on the first start; nothing needs to be run by hand.
</Callout>

## API Documentation

All Pro plugin API endpoints are documented in the [Studio CE API Reference](https://docs.studio.roadbeat.dev/api-reference/overview). Pro endpoints use the `/api/v1/pro/...` prefix and are included in the Swagger UI at `http://localhost:3000/api/docs`.
