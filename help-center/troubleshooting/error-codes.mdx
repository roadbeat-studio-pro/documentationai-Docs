## Overview

Every error a Studio Pro plugin API returns carries a stable, machine-readable **`code`** and the values of its message in **`params`**. The English `message` is a fallback for people reading raw responses; clients should decide on `code`.

- **API clients** switch on `code` instead of parsing English text, and read the details (which provider, which limit, which state) from `params`.
- **The Pro screens** translate the code into the interface language — all 24 EU languages — filling in `params`.

<Callout kind="info">
  Codes are stable identifiers — unlike the English message, which may be reworded. New codes can appear with new features, so always handle an unknown `code` by falling back to the HTTP status.
</Callout>

## The error body

Studio's global error filter turns every error — from CE and from every Pro plugin — into the same JSON body:

```json
{
  "statusCode": 502,
  "error": "Bad Gateway",
  "code": "AI_PROVIDER_FAILED",
  "message": "AI provider 'Mistral (EU)' failed (HTTP 503)",
  "timestamp": "2026-11-07T22:15:58.412Z",
  "path": "/api/v1/pro/ai/assist",
  "requestId": "6f1c2a9e-4b7d-4e55-9a51-0c2f8d3e7b10",
  "params": { "provider": "Mistral (EU)", "status": 503 }
}
```

<ResponseField name="statusCode" field-type="integer" required="true">
  The HTTP status, repeated in the body.
</ResponseField>

<ResponseField name="error" field-type="string" required="true">
  The HTTP reason phrase (`Bad Request`, `Not Found`, …).
</ResponseField>

<ResponseField name="code" field-type="string" required="true">
  The stable error code. Specific codes such as `AI_PROVIDER_FAILED` come from the plugin; when a plugin did not set one, a generic code derived from the status is used (see below).
</ResponseField>

<ResponseField name="message" field-type="string | array" required="true">
  English explanation. For request-validation failures (`VALIDATION_FAILED`) it is an **array** with one entry per failed rule.
</ResponseField>

<ResponseField name="params" field-type="object">
  The values interpolated into the message — e.g. `{ "provider": "Mistral (EU)", "status": 503 }`. Present whenever the code has parameters.
</ResponseField>

<ResponseField name="errors" field-type="array">
  Per-field details (`path`, `message`, `keyword`) for `422` content-validation errors.
</ResponseField>

<ResponseField name="timestamp" field-type="string" required="true">
  ISO 8601 time of the error.
</ResponseField>

<ResponseField name="path" field-type="string" required="true">
  The request path.
</ResponseField>

<ResponseField name="requestId" field-type="string" required="true">
  The request's correlation id, also sent as the `X-Request-Id` response header. Quote it when you report a problem — server logs are keyed by it.
</ResponseField>

<Callout kind="alert">
  The filter forwards **only** `params`. Other top-level fields a plugin attaches to an exception never reach the client — read every value from `params`. Outside production (`NODE_ENV` not `production`) the body additionally contains a `stack` field; never rely on it.
</Callout>

### Generic codes

When an error carries no specific code, the code is derived from the status:

| Status | Code | Notes |
|---|---|---|
| `400` | `VALIDATION_FAILED` | The request body failed validation; `message` lists each problem (e.g. `property isDefault should not exist` for a field the endpoint does not accept) |
| `400` | `BAD_REQUEST` | Any other bad request |
| `401` | `UNAUTHORIZED` | Missing or invalid JWT |
| `403` | `FORBIDDEN` | Your role may not do this |
| `403` | `ACTION_PREVENTED` | A plugin vetoed the action (for example a workflow publish guard or an Integration Hub publish guard); `message` is the reason |
| `404` | `NOT_FOUND` | Unknown resource — also a path id that is not a valid UUID in the Integration Hub |
| `409` | `CONFLICT` | Conflicting state |
| `429` | `TOO_MANY_REQUESTS` | Rate limited |
| `500` | `INTERNAL_ERROR` | Unexpected error; the message is always `Internal server error` and the cause is only in the server log |
| `502` / `504` | `UPSTREAM_UNAVAILABLE` | An upstream service failed |
| `503` | `SERVICE_UNAVAILABLE` | Temporarily unavailable |

## Handling errors in a client

Successful responses arrive in the `{ "data": … }` envelope; errors arrive in the body above. A small client wrapper covers both:

```typescript
interface StudioError {
  statusCode: number;
  code: string;
  message: string | string[];
  params?: Record<string, unknown>;
  requestId?: string | null;
}

class StudioApiError extends Error {
  constructor(readonly body: StudioError) {
    super(Array.isArray(body.message) ? body.message.join('. ') : body.message);
  }
}

async function studio<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`https://studio.example.com/api/v1${path}`, {
    ...init,
    headers: {
      Authorization: `Bearer ${process.env.STUDIO_TOKEN}`,
      'Content-Type': 'application/json',
      ...init.headers,
    },
  });
  if (!res.ok) throw new StudioApiError((await res.json()) as StudioError);
  return ((await res.json()) as { data: T }).data;
}

try {
  const result = await studio('/pro/ai/assist', {
    method: 'POST',
    body: JSON.stringify({ action: 'shorten', text: 'A long paragraph …' }),
  });
} catch (err) {
  if (!(err instanceof StudioApiError)) throw err;
  const { code, params, statusCode } = err.body;
  switch (code) {
    case 'AI_CONSENT_REQUIRED':
      // params.providerTypes: string[] — an admin has to grant consent first
      break;
    case 'AI_RATE_LIMITED':
    case 'AI_PROVIDER_FAILED':
    case 'AI_PROVIDER_UNREACHABLE':
    case 'AI_NO_HEALTHY_PROVIDER':
      // transient — retry with backoff
      break;
    default:
      // unknown code: decide on the status
      if (statusCode >= 500) {
        // retry later
      } else {
        throw err; // a 4xx will fail the same way again
      }
  }
}
```

<Callout kind="tip">
  Retry `429`, `502`, `503`, and `504` with exponential backoff. Do not retry other `4xx` responses unchanged — fix the request, the permissions, or the configuration the code points to.
</Callout>

## How the Pro screens show errors

Each plugin's interface catalog has a text per code under `errors.codes.<CODE>`, translated into all 24 EU languages. A Pro screen picks the message to show in this order:

<Steps>
  <Step title="The translated code" icon="languages">
    `errors.codes.<CODE>` from the plugin's catalog, with `params` filled in — e.g. *The AI provider “Mistral (EU)” returned an error (HTTP 503).* Generic codes (`BAD_REQUEST`, `NOT_FOUND`, …) are skipped here, because the server message is more specific.
  </Step>
  <Step title="The API message" icon="message-square">
    The English `message` from the response — except for `INTERNAL_ERROR`, `SERVICE_UNAVAILABLE`, and `UPSTREAM_UNAVAILABLE`, where the screen's own context text is more useful than "Internal server error".
  </Step>
  <Step title="The screen's own text" icon="file-text">
    The action-specific fallback, such as *The workflow could not be saved.*
  </Step>
  <Step title="A generic message" icon="alert-circle">
    `errors.unexpected` — *Something went wrong. Please try again.*
  </Step>
</Steps>

For `ACTION_PREVENTED`, the API message is the specific veto reason and is shown as is.

## Special cases

<ExpandableGroup>
  <Expandable title="AI chat stream: errors arrive as an SSE event" default-open="false">
    `POST /api/v1/pro/ai/chat` streams Server-Sent Events, so the HTTP status is already `200` when a failure occurs — including pre-call refusals such as missing consent or an exhausted budget. The error arrives as an `error` event with the same fields, then the stream closes:

    ```text
    event: error
    data: {"code":"AI_BUDGET_EXCEEDED","message":"AI org month budget exceeded","params":{"scope":"org","period":"month"}}
    ```

    An error without a code is sent as `INTERNAL_ERROR` with the message `Internal server error`; the details stay in the server log. See [Errors in the chat stream](/plugins/ai#errors-in-the-chat-stream).
  </Expandable>

  <Expandable title="Content locking: a clash is not an error status" default-open="false">
    `POST /api/v1/pro/locking/content/:contentId/lock` answers `201` even when another user holds an exclusive lock. The body then has `success: false` and `code: "LOCKED_BY_OTHER"`; an advisory lock held by someone else gives `success: true` with `code: "ALSO_EDITING"`. Both carry `params.userName`.
  </Expandable>

  <Expandable title="Malformed ids" default-open="false">
    A path id that is not a valid UUID never causes a `500`. The Integration Hub answers `404 NOT_FOUND` for it; the AI gateway answers the specific not-found code of the resource (`AI_PROVIDER_NOT_FOUND`, `AI_PROMPT_NOT_FOUND`, `AI_JOB_NOT_FOUND`).
  </Expandable>

  <Expandable title="Protocol endpoints: codes without screen texts" default-open="false">
    Endpoints that machines call — SAML and OIDC callbacks, SCIM 2.0 provisioning, inbound webhooks (`POST /api/v1/hooks-pro/:slug` and the incoming webhooks of Advanced Webhooks), and the GraphQL and GraphQL Delivery APIs — return codes too, but no Pro screen shows them, so they have no catalog text. Their English `message` is the explanation. SCIM endpoints answer with the statuses RFC 7644 prescribes (for example `409` for an existing `userName`, `400` for an unsupported filter), but in Studio's standard error body: the SCIM `detail` text is not passed on, and `message` reads `Http Exception`. See [SSO Integration](/plugins/sso).
  </Expandable>
</ExpandableGroup>

The tables below list every code of the AI gateway and the Integration Hub, and the codes of the other plugins that admins and integrators run into most. The complete, current set of codes with a screen text is each plugin's English catalog, served by your Studio:

```bash
curl https://studio.example.com/api/v1/plugins/pro-workflows/ui/i18n/en.json
# → the "errors.codes" object lists every code with its text
```

Codes that are not in a catalog are protocol or developer errors; their English `message` explains them.
